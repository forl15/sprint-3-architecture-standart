# ADR-002. Передача актуальных депозитных ставок в системы кол-центров

## Название задачи

Передача актуальных депозитных ставок в систему кол-центра банка и систему партнёрского кол-центра.

# Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| UC1 | Сотрудники депозитного и кредитного подразделений, АБС | Изменение депозитных ставок | Сотрудник изменяет или утверждает депозитные ставки в АБС. После сохранения изменения становятся доступны для публикации. |
| UC2 | Rate Synchronizer, Kafka, Rate Service | Публикация ставок | После изменения ставок сервис Rate Synchronizer получает изменения из АБС, публикует событие `RatesChanged` в Kafka, а Rate Service обновляет локальную копию ставок. |
| UC3 | Оператор кол-центра, Система кол-центра | Консультация клиента | Оператор получает актуальные депозитные ставки через API Rate Service и консультирует клиента. |
| UC4 | File Export Service, Партнёрский кол-центр | Передача ставок партнёру | После получения события `RatesChanged` автоматически формируется файл со ставками и передается партнёрскому кол-центру по SFTP. |
| UC5 | Партнёрский кол-центр | Консультация клиента | Оператор партнёрского кол-центра использует последний полученный файл для консультации клиентов по действующим депозитным ставкам. |

# Нефункциональные требования

|  №  | Требование |
|:---:| :- |
| R1  | АБС остается единственным источником истины (System of Record) для депозитных ставок. |
| R2  | Передача изменений ставок должна выполняться автоматически без участия сотрудников. |
| R3  | Передача ставок не должна создавать дополнительную нагрузку на Oracle БД АБС. |
| P1  | Формирование файлов не должно влиять на производительность АБС. |
| +R1 | Для асинхронного обмена сообщениями использовать Apache Kafka. |
| +R2 | Передача файлов партнёрскому кол-центру осуществляется по SFTP. |
| +R3 | Использовать существующий Rate Service, реализованный в ADR открытия депозитов. |
| +R4 | Не изменять существующую систему кол-центра подрядчика. |
| +R5 | Максимально использовать существующий стек технологий банка (Java Spring Boot, Oracle, MS SQL). |

# Решение

## Диаграмма контекста

[Диаграмма контекста](context.puml)

Диаграмма контекста включает следующие элементы:

- Сотрудники депозитного и кредитного подразделений;
- Автоматизированная банковская система (АБС);
- Платформа открытия депозитов;
- Система кол-центра банка;
- Партнёрский кол-центр.

---

## Диаграмма контейнеров

[Диаграмма контейнеров](containers.puml)

В состав решения входят следующие контейнеры:

| Контейнер | Назначение | Технологии |
|------------|------------|------------|
| Rate Synchronizer | Получает изменения ставок из АБС и публикует события | Java Spring Boot |
| Kafka | Передача событий между сервисами | Apache Kafka |
| Rate Service | Предоставляет REST API с актуальными ставками | Java Spring Boot |
| Rate DB | Хранит локальную копию ставок (Read Model) | MS SQL |
| File Export Service | Формирует файл ставок для партнёра и передает по SFTP | Java Spring Boot |

---

## Принятые архитектурные решения

### 1. АБС остается мастер-системой

Все изменения депозитных ставок выполняются исключительно в АБС. Это позволяет сохранить существующую бизнес-логику расчёта и согласования ставок и избежать дублирования функциональности.

---

### 2. Использование событийной архитектуры

После изменения ставок сервис **Rate Synchronizer** публикует событие `RatesChanged` в Kafka.

Использование Kafka позволяет:

- исключить прямую интеграцию нескольких систем с АБС;
- снизить нагрузку на Oracle;
- обеспечить слабую связанность компонентов;
- подключать новых потребителей ставок без изменения существующей архитектуры.

---

### 3. Использование Rate Service

Rate Service хранит локальную копию актуальных ставок (Read Model) и предоставляет REST API.

Система кол-центра банка получает ставки исключительно через этот сервис, что исключает обращения CRM к АБС и обеспечивает быстрое время отклика.

---

### 4. Передача ставок партнёрскому кол-центру

После получения события `RatesChanged` сервис **File Export Service**:

1. получает актуальные ставки из Rate Service;
2. формирует файл (CSV или XML);
3. передает файл партнёрскому кол-центру по SFTP.

---

# Альтернативы

## Альтернатива 1. Передавать ставки напрямую из АБС

**Недостатки**

- дополнительная нагрузка на Oracle БД;
- увеличение количества интеграций с критичной банковской системой;
- высокая связанность внешних систем с АБС.

---

## Альтернатива 2. Формировать файлы непосредственно в АБС

**Недостатки**

- усложнение АБС интеграционной логикой;
- увеличение нагрузки на банковскую систему;

---

## Альтернатива 3. Передавать файл по расписанию (например, один раз в сутки)

**Недостатки**

- партнёрский кол-центр использует устаревшие ставки;
- возможны ошибки при консультировании клиентов;
- отсутствует своевременная синхронизация изменений.

---


# Недостатки, ограничения, риски

1. Между изменением ставок в АБС и их появлением в системе кол-центра существует небольшая задержка, обусловленная асинхронной обработкой сообщений.

2. Передача файла зависит от доступности SFTP-сервера партнёра.

3. Партнёрский кол-центр получает обновления только после успешной передачи нового файла, поэтому существует небольшой риск использования предыдущей версии ставок до завершения синхронизации.
